# OmniaTV canary — 2026-08-10

## Environment

- WordPress 7.0.3
- PHP 8.3.6
- Newspaper 12.7.7
- tagDiv Composer 5.4.6
- Automattic Liveblog 1.12.2
- legacy WP Liveblog Appearance Layer 0.10.8 inactive

## Activation

Version 0.1.1 activated successfully on the primary site only (not network-wide). The shortcode smoke test rendered the integration slot successfully.

## Composer/frontend observations

Controlled Single Post Template canary against post `853492305` reported:

- the Liveblog block is available in Composer;
- one `#wpcom-liveblog-container` exists on the rendered page;
- that container is located inside `[data-tagdiv-liveblog-slot="1"]`;
- the controlled background setting did not affect the static Composer preview or frontend output;
- the DOM contained zero `.liveblog-entry` elements during the frontend check.

## Finding 1 — color handling

The initial renderer passed color values through `sanitize_hex_color()`. tagDiv's color picker supports RGBA values, so valid Composer colors containing transparency were silently discarded. Version 0.1.2 replaces the hex-only assumption with strict validation for tagDiv-compatible hex, RGB/RGBA and simple CSS custom-property references.

## Finding 2 — entries still require diagnosis

The successful single-root relocation does not by itself prove that the Liveblog React application received entries. Upstream Liveblog mounts React into `#wpcom-liveblog-container`, loads `window.liveblog_settings`, then requests page-one entries from its endpoint.

Before altering the relocation mechanism, the next canary check must establish:

1. whether post `853492305` contains Liveblog entries in WordPress;
2. whether `window.liveblog_settings` points to that same post;
3. whether the upstream `get-entries/1/latest` request returns entries;
4. whether React mounted inside the relocated root.

No production Single Post template should be changed until these checks pass.
